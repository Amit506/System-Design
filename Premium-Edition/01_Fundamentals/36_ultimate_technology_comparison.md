# 💯 THE MASTER CHEATSHEET: Ultimate Technology Showdown Tables

In System Design interviews, generic answers like "I will use a NoSQL database" or "I will use a Queue" will cause you to fail. Senior interviews require you to pick **specific** industry technologies and rigorously defend them using their exact architectural constraints, physical limitations, and mathematical pros/cons.

Below is the exhaustive, master comparison of every major technology across 7 technical pillars.

---

## 1. 🗄️ Databases & Storage Engines

| Technology / Paradigm | Specific Industry Pick | Specific Hyper-Optimised Pros | Highly Specific Cons & Algorithmic Limitations |
| :--- | :--- | :--- | :--- |
| **Monolithic Relational (SQL)** | **PostgreSQL** | Perfect MVCC (Multi-Version Concurrency Control) preventing reader-writer deadlocks. Deep JSONB indexing. Perfect ACID financial Ledgers. | B-Tree disk fragmentation under extreme write loads. Native Master-Master replication is deeply flawed (relies heavily on third-party active-passive failovers like Patroni). Cannot easily scale horizontally over 10TB without severe operational pain. |
| **Distributed SQL (NewSQL)** | **CockroachDB / Google Spanner** | True global Active-Active multi-region writes. $RPO=0$. Uses Raft consensus natively for every chunk of data. Synchronized True-Time (Spanner) or Hybrid Logical Clocks (Cockroach) for mathematically perfect distributed serializability. | Write latency is fundamentally bound by the speed of light—requires consensus across geographic regions (e.g., $100\text{ms}$ write latency minimum if nodes span the Atlantic). |
| **In-Memory Cache (Raw)** | **Memcached** | Pure, blistering fast multi-threaded RAM caching. Simpler and faster than Redis for basic string caching purely because it inherently uses multiple CPU cores. | Literally zero persistence to disk. Only supports bare-bones data types (String/Bytes). If the Docker container restarts, 100% of the cache is instantly evaporated. |
| **In-Memory Data Structure** | **Redis** | Native single-threaded Event Loop yields deterministic atomic execution without multi-threading locks. Advanced RAM structures (Sorted Sets for Leaderboards, HyperLogLog, Geospatial Indices). | Purely RAM bound (expensive). If AOF/RDB persistence lags during a sudden power outage, data loss of the last few seconds is mathematically guaranteed. The single-thread blocks if executing a slow $O(N)$ command like `KEYS *`. |
| **Disk Key-Value** | **Amazon DynamoDB** | $O(1)$ constant time lookups absolutely regardless of scale (1 Byte or 100 Terabytes). Fully managed Auto-Scaling serverless pricing. | Rigid access patterns. If you need to query by an attribute that is *not* a Partition/Sort Key, you must duplicate the data entirely into a GSI (Global Secondary Index), doubling your AWS bill. Hard 400KB limit per item. |
| **Wide-Column (LSM-Tree)** | **Apache Cassandra / ScyllaDB** | Peer-to-peer Masterless architecture (Gossip protocol). Zero SPOF. LSM-Trees allow blistering sequential write throughput capable of ingesting 100,000s of IoT metrics per second. | Extreme Eventual Consistency. Prone to "Tombstone" bloat (Deleted data must be kept as mathematical markers until periodic compaction). ScyllaDB is Cassandra rewritten in C++ (bypassing JVM garbage collection limits). |
| **Document Store** | **MongoDB** | Schema-less BSON storage allows rapid agile iteration. Natively supports automatic horizontal sharding via config-servers out of the box. | Denormalization mapping. Updating the name of a "Category" requires manually executing an `$updateMany` across 10,000 "Product" documents because 1-to-N SQL JOINS are actively discouraged. High RAM overhead. |
| **Graph Database** | **Neo4j** | Optimized mathematically for "Index-Free Adjacency". Every node physically points to its connected relationships in memory. Traversing a 6-degree deep social network is $O(1)$ per hop, vastly beating PostgreSQL `JOIN` explosions. | Abysmal at global aggregations. Finding "Friend of a Friend" is instant, but running `COUNT(*)` across all 1 Billion users requires scanning every node, crushing the CPU. Graph partitioning across multiple physical servers is an unsolved NP-hard problem. |
| **Full-Text / Analytics** | **Elasticsearch** | Inverted Indices enable instant fuzzy-text full-word matching, N-gram searches, and log aggregations. | The JVM Heap limit (requires $<32\text{GB}$ heaps to utilize compressed OOPs). Prone to "Mapping Explosions" if users dynamically add thousands of unique JSON fields, destroying the cluster memory. |
| **Time-Series (TSDB)** | **InfluxDB / Prometheus** | Native "Gorilla Compression" (Delta-of-Delta encoding). Can compress 30 days of repetitious temperature sensor integers into a few kilobytes. Native retention eviction policies. | Abysmal performance if you attempt to use it as an OLTP transactional store or attempt to perform complex relational joins. Immutable historical backfilling is very painful. |
| **Vector Database** | **Pinecone / Milvus** | Optimized mathematically for HNSW (Hierarchical Navigable Small World) graphs to perform extremely fast Cosine Similarity Approximate Nearest Neighbor (ANN) searches for LLM RAG pipelines. | Primarily stateless on the compute side. Does not handle standard CRUD scalar data reliably; requires syncing with a primary Truth DB (like Postgres). |
| **Bitmap Database** | **Pilosa / Roaring Bitmaps (RedisBitmaps)** | Stores boolean state (0/1) across millions of IDs instantly. Calculating "DAU (Daily Active Users)" for 100 Million users takes a few bytes of RAM using Bitwise `AND/OR` operations instead of counting SQL rows. | Extremely narrow use case. Cannot store arbitrary payloads or text—only binary presence flags associated with dense integer arrays. Sparse arrays waste massive memory unless perfectly compressed (Roaring). |

## 2. 📬 Message Queues & Event Streaming

| Technology Paradigm | Specific Industry Pick | Specific Hyper-Optimised Pros | Highly Specific Cons & Algorithmic Limitations |
| :--- | :--- | :--- | :--- |
| **Distributed Commit Log** | **Apache Kafka** | Immutability. Readers use an "Offset Pointer". Massive Consumer Fan-Out with zero performance degradation. Zero-Copy OS networking buffers enable millions of events/sec physically touching the SSD linearly. | Rigid partitions. If `Topic A` has 5 partitions, you can legally only have 5 concurrent consumers. Ordering is *only* mathematically guaranteed within a specific partition, not globally. (ZooKeeper/KRaft consensus complexity). |
| **Managed Stream** | **Amazon Kinesis** | AWS native. Integrates perfectly with Lambda Event Source Mappings. Out-of-the-box cross-region replication. | Hard physical limits (1 MB/sec Write, 2 MB/sec Read per shard). Significantly more expensive at hyper-scale than self-hosting Kafka. |
| **AMQP Message Broker** | **RabbitMQ** | Highly advanced routing via Exchanges (Header, Direct, Topic). Built-in "Push" mechanics. Workers buffer data locally until explicit ACKs. | Dequeue (deletion) mechanics. If a consumer ACKs a video upload task, the task physically vanishes from the Rabbit disk. You cannot 'rewind time' to replay failures like you can in Kafka. Queue bloat destroys the Erlang memory footprint. |
| **Serverless P2P Queue** | **Amazon SQS** | Complete operational invisibility. Infinite horizontal elasticity. Built intimately with Dead Letter Queues (DLQ). | Standard SQS allows duplicate deliveries and shuffled messaging order (due to distributed AWS storage internals). Strict ordering requires SQS FIFO, which drastically caps throughput to 300 (or up to 3000 batched) TPS. |
| **Serverless Pub/Sub** | **Amazon SNS** | Push-based notification system to HTTP endpoints, Email, SQS. | Not a queue. If SNS Pushes an HTTP webhook to a dead server, it tries incredibly briefly and then drops the payload entirely unless connected to an SQS buffer. |

## 3. 🌐 API Protocols & Networking

| Protocol Paradigm | Technology | Specific Hyper-Optimised Pros | Highly Specific Cons & Algorithmic Limitations |
| :--- | :--- | :--- | :--- |
| **Stateless Client/Server** | **REST (HTTP/1.1)** | Ubiquitous. HTTP status codes natively dictate state. Edge-CDN caching functions perfectly based solely on the URL and HTTP verb (`GET`). | The "N+1" Query problem. A mobile client might need Profile, Friends, and Posts, requiring 3 massive sequential HTTP round trips containing bloated JSON text. |
| **Query-Driven Graph** | **GraphQL** | Client dictates the exact payload shape. Solves under-fetching and over-fetching entirely. A single POST endpoint (`/graphql`) orchestrates massively nested resolver fetches. | Impossible to cache natively at the infrastructure Edge because every request is unique `POST` payload. Requires complex application-layer implementations (Apollo Dataloader) to prevent the backend from DDoS-ing its own database with repetitive queries. |
| **Binary RPC / HTTP/2** | **gRPC** | Utilizes HTTP/2 Multiplexing (sending thousands of parallel requests over a single TCP connection). Protobuf serialization shrinks payloads by 80% compared to JSON text. Strong static typing. | Human-unreadable binary. Heavily dependent on exact `.proto` schema files natively residing on both Client and Server. Not universally supported natively in older browsers without Envoy proxies (`grpc-web`). |
| **Persistent Bi-Directional** | **WebSockets** | True Full-Duplex. The server can physically push new Chat Messages to the client socket without the client polling. TCP connection remains intimately tied indefinitely. | Stateful layer nightmare. Breaks stateless Load Balancing (requires Sticky Sessions or Redis PubSub backplanes so Server A can push a message to Server B's connected socket). |
| **Persistent Uni-Directional** | **Server-Sent Events (SSE)** | Operates over standard HTTP/1.1. Native browser automatic reconnection logic. Perfect for live-updating Financial Tickers, ChatGPT streaming UI, or live sports scores (where the client only listens). | Half-Duplex limits. The client cannot send data up the SSE stream; they must execute a separate standard HTTP POST request. Maximum open connection limit in HTTP/1.1 browsers (traditionally 6 connections per domain). |
| **Transport Layer** | **UDP vs TCP vs QUIC** | **UDP:** No handshake, blind firing (Video Chat/Gaming). **TCP:** 3-way handshake, retransmission (Guaranteed delivery). **QUIC (HTTP/3):** Built on UDP but adds cryptographic stream isolation, eliminating TCP's "Head-of-Line Blocking" (where one lost packet stalls the entire HTTP connection stream). | QUIC requires significant CPU overhead for encryption and is aggressively throttled/dropped by archaic corporate firewalls that strictly expect TCP port 443 traffic. |

## 4. 💻 Compute Environments & Orchestration

| Tech Environment | System | Specific Hyper-Optimised Pros | Highly Specific Cons & Algorithmic Limitations |
| :--- | :--- | :--- | :--- |
| **Hardware VMs** | **Amazon EC2** | Complete OS isolation. Deep kernel tuning (e.g., custom `sysctl` TCP buffers). Perfect for massive databases (Postgres) that require dedicated, unshared NVMe SSD IOPS. | Abysmal elasticity. Booting a new EC2 VM requires full BIOS and OS Linux initialization (taking 2 to 5 minutes), completely ruining reactive auto-scaling to sudden traffic spikes. |
| **Container Orchestration** | **Kubernetes (K8s)** | Natively declarative. You define "I want 50 Pods", and the `etcd` Control Plane mathematically forces reality to match the desired state natively. Pods boot in milliseconds. | Deep abstraction taxes. The `kube-proxy` iptables and CNI (Container Network Interface) overlay networks add subtle processing latency. Upgrading a production K8s cluster historically risks immense downtime if `etcd` corrupts. |
| **V8 Isolate Edge Compute** | **Cloudflare Workers** | Physically executes code strictly within the globally distributed CDN Edge nodes ($<5\text{ms}$ away from users). Extremely low latency. Uses V8 Isolates instead of full Docker containers, yielding $0\text{ms}$ cold starts. | Cannot execute heavy binary files or non-JS/WASM languages. Extremely aggressive CPU duration limits (e.g., script must terminate in $50\text{ms}$). |
| **Function as a Service** | **AWS Lambda** | Infinite scaling from 0 to 10,000 parallel invocations instantly. Event-driven glue (native triggers from S3 uploads or DynamoDB streams). Pay *strictly* per 100-millisecond execution slice. | **The Cold Start Penalty.** If an environment hasn't been fired recently, AWS must provision a microVM natively (Firecracker), download the deployment zip, and initialize the language runtime. Java/Spring Boot Lambda cold starts can take 5+ seconds, ruining synchronous user HTTP APIs. Strict 15-minute max execution limit. |

## 5. ⚙️ Backend Languages (Scale Constraints)

| Language | Paradigm | Best For | Technical Strengths | Mathematical & Systemic Constraints |
| :--- | :--- | :--- | :--- | :--- |
| **Node.js** | Single-Threaded Event Loop | I/O Heavy Apps, API Gateways, Chat | Non-Blocking asynchronous I/O multiplexes thousands of database network hops onto a single CPU core almost effortlessly. | If a developer introduces a heavy CPU-bound loop (e.g., cryptographic hashing), the *entire single thread physically freezes*, instantly DoS-ing all other concurrent users connected to that Node instance. |
| **Java** | Multi-Threaded JVM | Financial Core, Hadoop Big Data, Complex State | Rock-solid thread pools. JIT (Just in Time) compilation optimizes running bytecode natively into machine code over days of uptime. | **Garbage Collection (GC) "Stop-The-World" Pauses.** The JVM physically halts all threads for hundreds of milliseconds to sweep RAM. This fundamentally excludes Java from High-Frequency Trading (HFT) where a $100\text{ms}$ total system freeze costs millions. |
| **Go (Golang)** | Compiled, Goroutines | Proxies, Kubernetes mesh, Concurrent scrapers | `Goroutines` are managed by the Go runtime natively, consuming roughly 2KB of RAM each (compared to Java's 1MB OS threads). You can spawn 1 Million Goroutines on a laptop. Blistering compile times. | Explicitly lacks deep Object-Oriented paradigms (Inheritance) which heavily frustrates organizing massive million-line enterprise DDD (Domain Driven Design) monoliths. |
| **Rust / C++** | Compiled, Zero-cost | Trading Engines, DB Storage Engines, Game Engines | Affords the user explicit raw physical memory allocation (Malloc) without any underlying Garbage Collection background daemon stealing CPU cycles. Absolutely deterministic speeds. | Unbelievably low developer velocity. The Rust "Borrow Checker" rigorously forces developers to prove memory safety at compile-time, resulting in steep learning curves and slow shipping times for simple CRUD apps. |
| **Python** | Interpreted, GIL | ML Data Pipelines, Rapid Web (FastAPI) | Integrates natively with underlying C-libraries (NumPy/TensorFlow) for matrix math, giving Python C-level ML performance with a beautiful high-level scripting syntax. | **The Global Interpreter Lock (GIL).** The CPython runtime mathematically prevents multiple native threads from executing Python bytecodes at once. True vertical multi-core scaling in a single Python process is fundamentally impossible; it requires aggressive multi-processing (spawning entirely separate isolated OS processes). |

## 6. 🚦 Proxies, Gateways & Traffic Management

| Tool | Paradigm | Best For | Specific Pros | Specific Constraints |
| :--- | :--- | :--- | :--- | :--- |
| **NGINX** | Reverse Proxy | Static file serving, SSL Termination, Basic Caching | Extremely lightweight event-driven C architecture. Unmatched reliability as a perimeter ingress controller. | Dynamic configuration natively requires physically rewriting the `nginx.conf` file on disk and reloading the master process, causing micro-blips. (Fixed mostly in costly NGINX Plus). |
| **Envoy** | Cloud-Native Proxy | Service Mesh (Istio), K8s Sidecars | Written in C++, heavily designed natively for dynamic API-driven configuration (xDS APIs). Natively supports observability, retries, circuit breaking at the L7 layer out-of-the-box. | Extreme configuration complexity. A raw Envoy YAML configuration file is thousands of lines of deeply nested esoteric routing rules. |
| **HAProxy** | L4/L7 Load Balancer | Database Load Balancing, Raw TCP routing | The absolute gold standard for extreme throughput pure L4 (Transport Layer) TCP load balancing. Consumes microscopic CPU. | Lacks the deep modern plugin ecosystem and L7 GraphQL/gRPC mutation features found in Envoy or Kong. |
| **Kong** | API Gateway | Rate Limiting, JWT Auth, Monetization API portals | Built dynamically on top of NGINX / OpenResty. Supercharged with extensible Lua scripting plugins to intercept and mutate traffic on the fly. | Heavily dependent on an underlying database (PostgreSQL/Cassandra) to synchronize its configuration state across the gateway cluster, introducing an external point of failure. |

## 7. 📈 Big Data Processing & Data Warehousing
Extracting, transforming, and querying massive Petabyte analytical datasets.

| Technology | Paradigm | Best For | Specific Hyper-Optimised Pros | Highly Specific Cons & Algorithmic Limitations |
| :--- | :--- | :--- | :--- | :--- |
| **Apache Spark** | In-Memory Batch & Micro-batching | Huge Data Engineering pipelines (ETL/ELT), Machine Learning. | Extremely resilient in-memory Resilient Distributed Datasets (RDDs). 100x faster than legacy Hadoop MapReduce by not aggressively writing intermediate shuffle steps to physical disk. | Heavy JVM/Scala footprint. Spark Streaming is actually *micro-batching* under the hood (processing chunks every 500ms), NOT true millisecond streaming. |
| **Apache Flink** | True Native Stream Processing | Live Fraud Detection, Real-time clickstream aggregations. | Native stateful stream processing. Flink processes events exactly as they arrive physically, providing true sub-millisecond latency (vastly superior to Spark Streaming). | Extremely complex state management (Checkpoints & Savepoints) required to ensure Exactly-Once processing guarantees natively across distributed workers. |
| **Snowflake** | Cloud Data Warehouse | OLAP analytical queries across massive corporate datasets over Petabytes. | Utterly separates Storage (AWS S3 natively) from Compute (Virtual Warehouses). You can scale the Storage boundlessly without paying for idle Compute processors. | Extreme vendor lock-in and profoundly unpredictable compounding costs. Users are metered on fractional per-second compute credits rather than flat hardware leasing. |
| **Google BigQuery** | Serverless Columnar Warehouse | Ad-hoc immense data crunching (Scanning Petabytes in seconds). | Purely Serverless execution natively. Uses Dremel execution trees to distribute SQL query execution across thousands of Google internal anonymous servers simultaneously. | You pay *per byte scanned* per query mathematically. A poorly optimized `SELECT *` without explicit partitioning limits on a multi-terabyte table can cost thousands of dollars instantly. |
