# Part 17: Big Data Analytics & Storage (OLTP vs OLAP)

A massive chunk of modern system design involves moving data out of the primary application database and into structures optimized for Business Intelligence, Machine Learning, and Big Data queries.

---

## ⚔️ 1. OLTP vs. OLAP

You must explicitly separate your transactional traffic from your analytical traffic.

### OLTP (Online Transaction Processing)
This is your standard application database (e.g., PostgreSQL, MongoDB, Cassandra).
*   **Purpose:** Operating the live business.
*   **Queries:** `INSERT`ing a new user, `UPDATE`ing an account balance, `SELECT`ing one user's profile.
*   **Characteristics:** Millions of tiny, sub-millisecond transactions. Highly concurrent. Requires strict ACID guarantees or extreme write throughput.

### OLAP (Online Analytical Processing)
This is your Data Warehouse (e.g., Snowflake, Amazon Redshift, Google BigQuery).
*   **Purpose:** Understanding the business.
*   **Queries:** `SELECT SUM(sales) FROM transactions GROUP BY region, month WHERE year = 2023`.
*   **Characteristics:** A small number of massive, incredibly complex read queries that scan terabytes of historical data. They take seconds to minutes to run.

**The Disaster Scenario:** If a Data Scientist runs a massive OLAP query on the live OLTP database, it locks the tables, spikes the CPU to 100%, and crashes the application for all real users. *Never mix OLTP and OLAP workloads.*

---

## 🏭 2. Data Warehouses vs. Data Lakes

Once data is generated by the app, where does it go for analytics?

### A. The Data Warehouse (Structured Analytics)
**Examples:** Snowflake, Amazon Redshift, Google BigQuery.

*   A centralized repository of integrated data from one or more disparate sources.
*   **Schema-on-Write:** Extremely rigid. Data must be cleaned, transformed, and forced into a pre-defined tabular schema *before* it can be inserted into the warehouse. (This process is called **ETL** - Extract, Transform, Load).
*   **Storage Mechanism:** Columnar storage format. If you run a query like `SELECT AVG(salary) FROM employees`, the warehouse only reads the tiny "salary" column off the disk, skipping the massive "bio" or "address" columns.
*   **Use Cases:** Highly structured business reporting, financial dashboards, predictable SQL-based BI tools.

### B. The Data Lake (Raw Storage)
**Examples:** Amazon S3 (Raw), Hadoop HDFS, Azure Data Lake.

*   A massive, cheap storage repository holding a vast amount of raw data in its native format (JSON logs, raw text, CSVs, image blobs, audio files).
*   **Schema-on-Read:** There is no strict schema. You just dump everything into the lake. You only apply structure and formatting to the data at the exact moment you are running a query against it.
*   **Use Cases:** Machine Learning training (which requires massive sets of raw images/text), archiving application logs, unstructured data exploration.

### C. The Evolution: The Data Lakehouse
**Examples:** Databricks, Apache Iceberg, Delta Lake.
*   A modern architecture combining the flexibility, raw storage, and cheap cost of Data Lakes with the ACID transactional management and SQL performance of Data Warehouses.

## 🌊 3. Big Data Processing (Hadoop & Spark)

How do you analyze a 50 Terabyte log file sitting in an S3 Data Lake? You can't load it into Python on a single server; it will crash instantly. You need distributed processing.

### MapReduce (The Legacy Standard)
Pioneered by Google and Apache Hadoop. It splits a massive analytical task across 1,000 cheap commodity servers.
1.  **Map:** Break the 50TB file into 1,000 tiny chunks. Send each chunk to a separate server. The server processes its chunk independently.
2.  **Shuffle/Sort:** Group the intermediate results.
3.  **Reduce:** Aggregate the output from the 1,000 servers into a single final answer.
*   *Flaw:* It writes intermediate data to the physical hard drive constantly, making it very slow for iterative tasks.

### Apache Spark (The Modern Standard)
The successor to MapReduce.
*   **The Magic (In-Memory Processing):** Spark keeps the massive distributed datasets entirely in RAM (Memory) across the cluster, rather than writing to disk.
*   It is up to 100x faster than Hadoop MapReduce for complex Machine Learning training or iterative data analytics.
*   **Streaming vs. Batch:** While traditional data systems run "Batch Jobs" (processing yesterday's data every night at 2 AM), tools like Spark Streaming or Apache Flink can ingest endless streams of data from Kafka, analyze it continuously in real-time, and detect anomalies instantly.
